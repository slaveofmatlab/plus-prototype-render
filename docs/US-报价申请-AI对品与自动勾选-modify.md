# 报价申请 - AI 对品与自动勾选（详情修改用户故事）

## 1. 基本信息

- **需求名称**：报价申请详情-明细录入 AI 对品与自动勾选
- **所属模块/子模块**：销售管理模块 / 报价申请
- **功能路径**：`requirements/报价申请/详细/新增报价申请/`（PC 新建报价申请向导 + 详情新增模式）
- **关联 US**：`US-报价申请.md`（报价申请详情，本 US 为在其「新增」模式基础上的修改）
- **变更概览**：在新增报价申请录入明细环节，新增「客户报价单上传」入口，用 AI 自动完成商品解析、预处理与标准产品对品并回填明细；同时根据对品结果自动勾选报价品类、预置采购基准价模式，替代原有的人工逐条录入/匹配与手工勾选，降低录入成本、提升对品准确率。

## 2. 变更范围总览

| 变更类型 | 变更说明 |
| --- | --- |
| 明细信息 | 新增「客户报价单上传」入口，上传后自动解析→预处理→对品→回填明细 |
| 明细信息 | 替换「标准产品匹配」算法（Dice 二元组 → 预处理 + BM25/Bigram 双路召回 + 置信度） |
| 页面逻辑 | 新增「根据对品结果自动勾选报价品类」 |
| 页面逻辑 | 新增「自动勾选品类默认预置采购基准价模式」 |

> 角色权限、数据权限、单据状态机、价格计算等**均沿用现有报价申请口径，本次不调整**。

> ⚠️ **与「导入产品」功能的关系（重要）**：本 US 新增的「客户报价单上传（AI 自动对品）」与系统现有「导入产品（固定模板导入，见原 PRD §8.4.6）」是**两个独立功能，需同时保留、互不替代**。参考实现原型（plus-prototype-render）中二者曾共用同一上传入口，属原型实现层面的合并；正式开发时须拆分为两个独立入口：
> - 「导入产品」：按固定模板批量导入，有标准产品代码则直配、不走相似度匹配。
> - 「客户报价单上传」：上传客户原始报价单，AI 自动识别商品列 → 预处理 → 对品。

## 3. 变更详细说明

### 3.1 客户报价单上传（明细信息变更，新增）

- **变更前**：明细行通过「添加产品」弹窗（从产品库选）、「获取参考客户产品」、「导入产品（模板）」等方式录入，客户报价单（Excel）无法直接录入，需人工逐条誊录与匹配。
- **变更后**：在 PC 新建报价申请向导「第一步·基础信息」底部，新增「客户报价单上传区」。

**上传区交互规则**：

| 项 | 规则 |
| --- | --- |
| 位置 | 新建向导第一步「基础信息」底部 |
| 文案 | 点击或拖拽上传客户报价单、定价单、询价单 |
| 支持格式 | `.xlsx` / `.xls`（`.csv` 待确认） |
| 处理方式 | 后台异步处理 + 前端轮询进度（进度条 + 百分比），不做同步长请求（大批量上千条会超时） |
| 结果回填 | 每条商品写入明细行：客户产品名称、标准产品名称/编码、品牌、规格、一级分类、匹配置信度、匹配候选 |
| 错误处理 | 文件解析失败/列识别失败/无可匹配标准品时给出明确提示，允许人工调整，不整单失败 |

**后端处理链路**（上传后自动完成）：

```
上传 Excel
  → 解析：自动识别表头行 + 商品名称列（规则优先，规则失败 AI 兜底）
  → 客户格式自动判定（基于文件内容，不依赖客户名）
  → 商品名预处理（普通 or 特殊两套管线，见 3.2）
  → 标准产品对品（见 3.2）
  → 历史报价 + 采购价查询（价格沿用 plus 系统现有取价逻辑自动带出）
  → 返回匹配结果，前端回填明细表
```

### 3.2 标准产品匹配算法（明细信息变更，替换）

- **变更前**：Dice 二元组加权，名称 40% + 品牌 35% + 规格 25%，取综合分最高 **Top5** 候选。
- **变更后**：预处理 → 双路召回 → 重排 → 置信度，返回 **Top10** 候选。

**3.2.1 商品名预处理（两套管线，自动分流）**

按**文件内容自动判定**走哪套（不依赖客户名判断）：

| 类型 | 判定特征 | 处理管线 |
| --- | --- | --- |
| 普通客户 | 常规中文品名 | 6 步清洗 + 智能分词 + 品牌检测 |
| 特殊客户（酒店投标格式） | 英文大写前缀 + 含中文 + 末尾括号含中文（如 `JUICE ALOE VERA (OKF) ... 果汁 ...`） | 中英双语清洗（香格里拉式） |

- 普通客户 6 步清洗：全角→半角、单位归一化（kg→g、L→mL）、包装归一化、去品牌名后缀、去括号保留内容、散称术语统一；后续智能分词（贪心 + DP + jieba）+ 品牌检测。
- 特殊客户清洗：繁体→简体（OpenCC）、定位中文去英文、去品类前缀、去储存类型+国家名、去包装描述（PER PKT/BTL/BAG）、括号内品牌加「牌」后缀。

**3.2.2 对品算法**

| 步骤 | 说明 |
| --- | --- |
| 双路召回 | BM25（core_tokens）top200 + Bigram（core_name，字符 2-gram）top200，取并集 |
| 品牌过滤 | 查询含品牌时仅保留同品牌候选；候选不足 5 条时跳过过滤 |
| 多维重排 | `base(0.6×BM25_norm + 0.4×Bigram_norm) + spec_bonus(≤0.5) + attr_bonus(≤0.15) + brand_bonus(0.35) + bulk_bonus(0.3)` |
| 置信度 | `品牌 0.25 + 规格 0.25 + 核心名(bigram Dice 系数) 0.5`（按参与维度自动归一化），区间 0~1 |
| 置信度标签 | 高（≥0.7）/ 中（≥0.4）/ 低（<0.4）/ 无匹配 |
| 候选数量 | Top10（原 Top5），用于「调整标准产品匹配」弹窗，展示综合得分/置信度/分项维度，支持重新匹配 |

**3.2.3 性能要求（硬性）**

- 启动时主数据字段预提取为 Python list，查询 O(1) 索引，**禁止热路径 DataFrame 全表扫描**（单条候选扫 3.2 万行会导致上千条超时）。
- 预处理结果缓存复用，避免同一条商品重复归一化。
- 大批量（上千条）必须异步 + 进度，不能同步阻塞。

### 3.3 自动勾选品类 + 默认采购基准价模式（页面逻辑变更，新增）

- **变更前**：报价品类由用户手工勾选；采购基准价模式由用户在品类矩阵/明细中手工选择。
- **变更后**：对品完成后，系统自动完成两项前置操作：

**3.3.1 自动勾选报价品类**

- 依据：每条匹配结果的**一级分类（cat1）**。
- 规则：将本次结果出现过的 cat1 映射为页面「报价品类」，自动勾选对应复选框（已勾选不重复勾）。
- 映射（后端一级分类 → 页面报价品类，注意几处名称不同）：

| 后端 cat1 | 页面报价品类 |
| --- | --- |
| 米面油 / 干调类 / 冻品类 / 调理类 / 蔬菜类 / 休闲食品 / 豆制品 / 禽蛋类 / 牛羊肉 / 鲜禽类 / 鲜猪肉 / 奶制品 | 同名 |
| 水饮类 | 饮料 |
| 水果类 | 水果 |
| 鲜水产 | 水产 |

> 映射关系开发时应从主数据/字典读取，不硬编码前端。

**3.3.2 默认采购基准价模式**

- 对「本次自动勾选、且尚未设置过模式」的品类，默认预置采购基准价模式为 **「采购价格」**。
- ⚠️ 命名对齐：原 PRD §9.4.1 已把枚举从旧「采购价格(有效且最低)」改名为「采购价格」，开发以 PRD 新命名为准。
- 用户可后续手动改为其它模式（市调价格 / 网站价格 / 参考现客户价格）。

## 6. 验收标准（AC）

**AC1 上传自动对品主流程**
- Given 用户在新增报价申请向导上传一份含商品清单的 Excel 报价单
- When 系统完成解析与对品
- Then 明细表按行回填客户产品名称、标准产品名称/编码、品牌、规格、一级分类、置信度

**AC2 特殊客户自动分流**
- Given 上传的报价单商品名为中英双语酒店投标格式（如 `JUICE ALOE VERA (OKF) ... 果汁 ...`）
- When 系统判定处理模式
- Then 自动走特殊预处理（去英文/品类前缀/储存类型/国家），无需用户指定客户类型

**AC3 自动勾选品类**
- Given 对品结果含一级分类「米面油」「干调类」等
- When 结果回填完成
- Then 页面自动勾选对应报价品类复选框（水饮类→饮料、水果类→水果、鲜水产→水产）

**AC4 默认采购基准价模式**
- Given 系统自动勾选了若干报价品类
- When 勾选完成
- Then 这些品类默认采购基准价模式为「采购价格」，且用户可手动改为其它模式

**AC5 大批量不超时**
- Given 上传的报价单含 1000+ 条商品
- When 系统处理后端异步 + 前端轮询
- Then 页面展示进度条与百分比，处理不超时、不中断

**AC6 无匹配/失败可处理**
- Given 某条商品无法匹配标准产品，或文件解析/列识别失败
- When 系统返回结果
- Then 给出明确提示，允许用户手动调整或修正，不整单失败

**AC7 对品准确率回归**
- Given 一批真实客户报价单样本
- When 系统完成对品
- Then Top1 命中率与人工校正率达到业务约定的基线（上线前与业务对齐）

## 7. 假设前提与待确认事项

### 7.1 假设前提

- 报价申请现有状态机、价格计算、权限、数据权限逻辑不变，本 US 仅在其「新增」模式叠加 AI 对品能力。
- 标准产品主数据（约 3.2 万条 normalized 库）与预处理词库（规格词/属性词/品牌词）已具备，匹配算法可独立调用。

### 7.2 待确认事项

- **与「导入产品」功能拆分**：「导入产品（模板导入）」与「客户报价单上传（AI 对品）」须拆分为两个独立入口；原型中二者共用上传入口，正式开发时需拆分，避免老功能被替代。
- **上传格式**：本期是否包含 `.csv`（原型 UI 已写，后端仅实现 `.xlsx`/`.xls`）。
- **默认采购基准价模式**：确认为「采购价格」（PRD 新命名），是否允许产品级默认值可配。
- **词库/主数据更新机制**：上线后规格词、属性词、品牌词库及标准产品 normalized 库的刷新入口与频率。
- **AI 列识别兜底**：规则识别失败时用 LLM（DeepSeek）兜底，需确认是否启用及 API Key 配置。
- **对品准确率基线**：Top1 命中率/人工校正率的验收阈值需业务确认。
- **特殊客户范围**：酒店投标格式自动判定规则，新客户格式变化时是否需要扩展。
