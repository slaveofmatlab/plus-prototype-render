# PLUS 报价申请 —— AI 对品与自动勾选 需求方案

> 面向开发的需求说明。本文在既有《PRD-报价申请.md》（v2.1.0，见同目录 `原始PRD-报价申请.md`）基础上，新增三个改动点。
> 已有可运行参考实现：本仓库（`backend/` 为 FastAPI 后端 + HTML 前端原型，含完整预处理/对品算法与上传交互），开发可对照 `backend/` 落地。
> 原始基线 HTML 原型见 `backend/frontend/`（已含本次改动）；技术文档见根目录 `README.md`。

---

## 1. 背景与目标

现有报价申请的「标准产品匹配」沿用旧算法（Dice 二元组加权，名称 40% + 品牌 35% + 规格 25%，取 Top5）。业务上存在两个痛点：

1. 明细录入依赖人工一条条选品/匹配，客户发来的报价单（Excel）无法直接吃进去；
2. 旧匹配算法对真实客户品名（规格混杂、中英双语、品牌缩写）召回率和准确率不足，人工校正成本高。

本次目标：**让用户上传客户的报价单 Excel，系统自动完成「解析 → 预处理 → 标准产品对品 → 回填明细」，并自动勾选报价品类、预置采购基准价模式**，把人工操作降到最低。

三个改动点：

| 编号 | 改动点 | 性质 |
| --- | --- | --- |
| ① | 客户报价单上传入口 | 新增 |
| ② | 商品预处理 + 标准产品对品算法 | 替换旧 Dice 算法 |
| ③ | 自动勾选报价品类 + 默认采购基准价模式 | 新增 |

---

## 2. 改动点①：客户报价单上传入口（新增）

### 2.1 位置与交互

在 **PC 新建报价申请向导（`PRD.Quote-Request-New.html`，即原始 `PRD.新增报价申请.html`）第一步「基础信息」底部**，新增「客户报价单上传区」：

- 文案：`点击或拖拽上传客户报价单、定价单、询价单`
- 支持格式：`.xlsx` / `.xls`（后续可评估 `.csv`）
- 上传后进入处理状态（遮罩 + 进度条），**处理为后台异步**，前端轮询进度，避免大批量超时

### 2.2 处理流程（后端）

上传后触发一体化处理，链路：

```
上传 Excel
  → 解析：自动识别表头行 + 商品名称列（规则优先，规则失败 AI 兜底）
  → 客户类型/格式自动判定（基于文件内容，不依赖客户名）
  → 商品名预处理（普通 or 特殊两套管线）
  → 标准产品对品（见改动点②）
  → 历史报价 + 采购价查询（价格用plus系统现有逻辑自动带出的）
  → 返回匹配结果，前端回填明细表
```

### 2.3 交互细节

- **异步 + 进度条**：上传接口立即返回 `task_id`，前端每 1.5s 轮询进度接口，展示进度条 + 百分比（如「已处理 500/1566 条（32%）」）。**不要用同步长请求**，大批量（上千条）会超时。
- **结果回填明细表**：每条商品写入明细行，含客户产品名称、标准产品名称/编码、品牌、规格、一级分类、匹配置信度、匹配候选（用于「调整标准产品匹配」弹窗）等。
- **错误处理**：文件解析失败、列识别失败、无可匹配标准品时，给出明确提示；允许用户手动调整，不整单失败。

## 3. 改动点②：商品预处理 + 标准产品对品算法（替换旧 Dice）

### 3.1 旧算法（待替换）

原 PRD §8.4.4：`Dice 二元组加权，名称 40% + 品牌 35% + 规格 25%，取综合分最高 Top5 候选`。

### 3.2 新方案：预处理 → 双路召回 → 重排 → 置信度

#### 3.2.1 商品名预处理（两套管线，自动分流）

预处理在匹配前清洗客户品名，提升召回。**根据文件内容自动判定走哪套**（不依赖客户名判断）：

| 类型 | 判定特征 | 处理管线 |
| --- | --- | --- |
| 普通客户 | 常规中文品名 | 6 步清洗 + 智能分词 + 品牌检测 |
| 特殊客户（酒店投标格式） | 英文大写前缀 + 含中文 + 末尾括号含中文（如 `JUICE ALOE VERA (OKF) ... 果汁 ...`） | 香格里拉式中英双语清洗 |

**普通客户 6 步清洗**：
1. 全角→半角，统一乘号，去特殊字符，合并空格
2. 重量/体积/长度单位归一化（kg→g、L→mL、厘米→cm 等）
3. 包装归一化（`20包/箱` → `20包 箱`）
4. 去品牌名 + 后缀（牌/品牌/公司）
5. 去括号保留内容
6. 散称术语统一（散装称重→散称）

后续还有：智能分词（贪心 + DP + jieba 三级）、品牌检测（Aho-Corasick / 线性扫描）。

**特殊客户（酒店投标格式）清洗**：
1. 繁体→简体（OpenCC）
2. 定位中文起始，去英文部分
3. 去品类前缀（124 个品类词，最长匹配 + 保护逻辑）
4. 去储存类型（干货/冰鲜/急冻/常温）+ 国家名（~200 个）
5. 去包装描述（PER PKT/BTL/BAG 等）
6. 括号内品牌加「牌」后缀

#### 3.2.2 标准产品对品算法

数据库：标准产品主数据（约 3.2 万条，已预处理好的 normalized 版本）。

1. **双路召回**（取并集）：
   - BM25 索引（基于 core_tokens 分词）→ top200
   - Bigram 索引（基于 core_name 核心名，字符 2-gram）→ top200
2. **品牌过滤**：查询含品牌时，仅保留同品牌候选；候选不足 5 条时跳过过滤（防过拟合）。
3. **多维度重排**：
   ```
   final = base + spec_bonus + attr_bonus + brand_bonus + bulk_bonus
   base  = BM25_norm × 0.6 + Bigram_norm × 0.4
   spec_bonus  最高 +0.5（规格数字+单位匹配）
   attr_bonus  最高 +0.15（属性词命中）
   brand_bonus +0.35（品牌命中）
   bulk_bonus  +0.3（散称匹配）
   ```
4. **置信度评估**（独立于排序分，0~1；权重按参与维度自动归一化）：
   ```
   置信度 = 品牌 0.25 + 规格 0.25 + 核心名(字符 bigram Dice 系数) 0.5
   ```
   - 品牌：仅当订单或候选有品牌时参与——品牌匹配 1.0 / 订单无品牌结果有品牌 0.8 / 订单有品牌结果无品牌 0.1 / 不一致 0.0
   - 规格：仅订单有规格时参与——数值+单位匹配 1.0 / 数值匹配单位不同 0.7 / 结果无规格 0.2 / 数值不一致 0.5
   - 核心名：字符 bigram 的 Dice 系数（0~1）
   前端「匹配相似度」列以**置信度百分比（综合分）**展示匹配置信度（如「综合85%」），不区分高/中/低标签。

5. **候选返回 Top10**（原 Top5），用于「调整标准产品匹配」弹窗，展示综合得分、置信度、分项维度，支持重新匹配。

#### 3.2.3 性能要求（重要）

- 启动时把主数据字段预提取为 Python list，查询用 O(1) 索引，**禁止热路径上做 DataFrame 全表扫描**（原始实现踩过这个坑，单条候选扫 3.2 万行导致上千条必超时）。
- 预处理结果缓存复用，避免同一条商品重复归一化。
- 大批量（上千条）必须走**异步 + 进度**，不能同步阻塞。

## 4. 改动点③：自动勾选品类 + 默认采购基准价模式

对品完成后，根据匹配结果自动完成两项前置操作，减少人工：

### 4.1 自动勾选报价品类

- 依据：每条匹配结果的**一级分类（cat1）**。
- 规则：把本次结果中出现过的 cat1，映射为页面「报价品类」，自动勾选对应复选框（已勾选的不重复勾）。
- 映射关系（后端一级分类 → 页面报价品类，注意几处名称不同）：

| 后端 cat1 | 页面报价品类 |
| --- | --- |
| 米面油 / 干调类 / 冻品类 / 调理类 / 蔬菜类 / 休闲食品 / 豆制品 / 禽蛋类 / 牛羊肉 / 鲜禽类 / 鲜猪肉 / 奶制品 | 同名 |
| 水饮类 | 饮料 |
| 水果类 | 水果 |
| 鲜水产 | 水产 |

> 此映射表开发时应改为从主数据/字典读取，不要硬编码在前端。

### 4.2 默认采购基准价模式

- 对「本次自动勾选、且尚未设置过模式」的品类，默认预置采购基准价模式为 **「采购价格」**。
- ⚠️ 命名对齐：原 PRD §9.4.1 已把枚举从旧「采购价格(有效且最低)」改名为 **「采购价格」**。参考实现原型里写的是旧名，开发时以 PRD 新命名为准，枚举字典见 §9.4.1。
- 用户可后续手动改为其它模式（市调价格 / 网站价格 / 参考现客户价格）。

## 5. 后端接口设计（参考实现）

| 接口 | 方法 | 说明 |
| --- | --- | --- |
| `/api/preprocess_match` | POST | 上传文件（`multipart/form-data`：`file` + `customer_name` + `top_n`），启动后台处理，**立即返回 `task_id`** |
| `/api/preprocess_match/{task_id}/progress` | GET | 轮询进度；`status=done` 时返回 `results[]`（含 `raw_name / preprocessed_name / top_match / alternatives / quote / procurement`）及 `is_special` |

`results[].top_match` 关键字段：`product_code / product_name / confidence / score / detected_brand / normalized_spec / core_name / attributes / cat1 / unit / is_yihai / brand / spec`。

> 参考实现为 FastAPI 独立服务；正式落地时按 PLUS 系统既有技术栈（Spring Boot / 既有服务）承接同一套接口契约与算法，算法核心可复用参考实现。

## 6. 技术要点与风险

1. **算法服务归属**：预处理（归一化管线、特殊客户清洗）与对品（BM25/Bigram 索引）是一套相对独立的模块，建议作为独立服务或独立模块沉淀，与报价申请业务解耦。
2. **词库/主数据**：规格词、属性词、品牌词库，以及标准产品 normalized 库，需要有维护入口与更新机制（当前为静态 Excel 文件，上线后需规划数据刷新）。
3. **特殊客户范围**：酒店投标格式的判定基于「文件内容特征」，已覆盖香格里拉等多客户，不再按客户名硬编码；新客户格式变化时需评估判定规则是否仍覆盖。
4. **AI 列识别兜底**：当表头/商品列规则识别失败时，用 LLM（DeepSeek）兜底识别商品名称列；需配置 `DEEPSEEK_API_KEY`，无 key 时退化为纯规则识别（不报错）。
5. **单位换算**：对品结果需按明细行单位换算价格，口径对齐原 PRD §9.4.3.4。
6. **性能**：见 §3.2.3，异步 + 预提取字段是硬性要求。

---

## 7. 验收标准

- 上传一份客户报价单 Excel，系统自动识别表头/商品列，逐条完成预处理与标准产品对品，结果回填明细表。
- 对品结果展示 Top10 候选 + 置信度百分比（综合分），「调整标准产品匹配」弹窗可切换候选并重新匹配。
- 特殊客户（酒店投标格式，英文+中文双语）与普通客户自动分流处理，无需用户指定客户类型。
- 根据匹配结果自动勾选对应报价品类；自动勾选的品类默认采购基准价模式为「采购价格」。
- 大批量（如 1000+ 条）上传不超时，展示进度条；处理失败/无匹配给出明确提示且可人工调整。
- 匹配算法准确率：以真实客户报价单样本回归，Top1 命中率与人工校正率作为评估口径（上线前与业务对齐基线）。
